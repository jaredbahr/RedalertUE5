# RPC ingress budget for the native proof

`ServerSubmitCommand` applies a budget on each server-side `AProofPlayerController` before calling `SubmitForOwner`. The budget counts **every** dispatched request, including malformed payloads and replayed or skipped sequences. The command model's 32-commands-per-advance gameplay allowance is separate: its early malformed/sequence exits do not limit ingress work, reliable results, or result logs.

The proposed fixture defaults are a 64-request burst and 32 tokens replenished per second. The clock is monotonic (`FPlatformTime::Seconds`); a nonfinite or regressing timestamp cannot replenish tokens. These values bound result and log generation for one connection without affecting the four ordered commands in the existing native proof. They are implementation defaults, not measured throughput targets, game balance, or an internet capacity claim.

Each admitted request still goes through normal command validation and gets its existing `ClientCommandResult` receipt, including specific rejection reasons. The first request without a token latches that controller's budget, writes one `PROOF_INGRESS_LIMIT` warning, and closes its `UNetConnection`. Later dispatched requests on that controller return before model submission, acknowledgement, or logging. A server-local controller with no network connection is also latched, but cannot be disconnected by this adapter. The overflowing request has no reliable receipt: a receipt sent just before closing would not be guaranteed to arrive. The connection close is the explicit signal that the in-flight sequence is no longer usable. A new controller starts with a fresh budget and local command sequence; broader reconnection, owner cleanup, and resynchronization remain separate work.

This guard runs after Unreal's RPC decoding and reliable transport queueing. It limits this adapter's model/ack/log work per controller, not packet parsing, already queued network traffic, or repeated new connections. A production transport policy needs separate measurements and abuse handling.

`RedalertProof.Commands.IngressBudget` covers burst and refill boundaries, clock anomalies, latch behavior, and independent controllers. `RedalertProof.Commands.IngressFixture` covers the normal four ordered requests and a valid opener followed by malformed/duplicate requests across 65 attempts, including the bounded receipt count. These native tests exercise the pure budget and command route; the separate loopback fixture below verifies actual connection-close behavior and log evidence.

## Validation plan and fixture boundary

Baseline: `9ef377093c9eac3ca45b4e4670326efefe1b6a15` (`fix/owner-allocation`). The seven exact native groups include a first valid sequence followed by actual duplicate sequence 1, malformed sequence 0, token refill/clock/latch boundaries and the existing gameplay/owner tests.

`test-rpc-ingress.ps1` uses real reliable RPCs over UDP loopback: one healthy client first moves, another sends 128 malformed RPCs in one tick, the server observes the offending connection state as closed, and the client observes ConnectionLost. Only then does the script release healthy production; both its accepted receipt and replicated move/unit/credit outcomes must pass. The host must log exactly one ingress warning/close, model-result count must equal admitted count within the measured token budget, and no flooded-owner result may occur after closure. An engine reliable-buffer overflow or crash cannot satisfy the close proof. Receipts queued before closing need not reach the flooded client.

The native regression fixture retains its exact two-client command, ownership-rejection, bot, outcome and matching-revision gates. Test launchers use two allowed CPUs/Normal priority with process-identity checks and process-local asynchronous editor-game asset discovery; the new close fixture has a 90-second total deadline and the designated non-system drive cache/temp soft guards. These polls are not hard confinement or a zero-C-write guarantee. Build compiler actions are serialized. No visible game, new art, install or hosted build is needed. Actual execution identities/results are recorded below.
