## Reviewed source contract

- `AreaGuard = 10` is appended. `Submit` accepts only a live, owned Combat in a playing skirmish with `TargetUnitId = INDEX_NONE` and exact zero destination. The server copies that unit's current position into `AreaGuardPost`; a new accepted command reanchors. Rejections leave the prior state unchanged. The GameMode rejects stale epochs before `Model.Submit`.
- Four replicated unit fields hold Guard enabled, post, target ID, and returning. `ComputeDigest` includes every nondefault Guard combination and preserves old default-record digests. These fields travel inside the existing `FProofSnapshot`, not a private-order probe.
- Target selection uses the saved post, closed `2 * AttackRange` scan, hostile live-team filtering, nearest distance with UnitId tie break, and eligible previous-target retention. Movement uses the shared initial snapshot and one movement budget. A proposed chase endpoint beyond the closed `AttackRange` post leash switches to return within that same budget. Damage uses post-move positions and the strict weapon range; target loss/death resolves to return without a second shot or step. At the exact post, a later advance can reacquire.
- Accepted Move, Attack, AttackMove, and Stop clear Guard. Death, terminal order clearing, reset/reseed clear it; owner removal preserves a surviving guard post while making it return unless the match is terminal. During the first 20 simulated seconds, the bot offers Guard after economy/production within the existing four-command budget and avoids reanchoring an already guarded unit. The existing attack scheduler can replace it after grace.
- The PR68 manifest names exactly eight new groups: `AdmissionAndReplay`, `AcquireChaseReturn`, `LeashAndTargetLoss`, `OverridesAndLifecycle`, `DamageAndConservation`, `DigestAndLateObserver`, `PlannerAndGrace`, and `PublicModelPath`, all under `RedalertProof.Skirmish.AreaGuard`. Its declared total is 54 skirmish names. The published documentation reports portable/cloud tests; local UHT, Windows native tests, and runtime acceptance are still separate gates.

## Prepared observation path

`-ProofAreaGuardObserve -ProofAreaGuardRun=<32 hex> -ProofAreaGuardSource=<40 hex>` enables bounded `PROOF_AREA_GUARD_OBSERVATION` JSON on the dedicated skirmish host and each client. The run token must be unique to the composition; the source token must be the diagnostic checkout's `git rev-parse HEAD:unreal/Source`, recorded alongside build DLL hash. A missing/malformed token or row/byte cap exits as failure. One match epoch is allowed. The flag is rejected for non-dedicated host or incompatible skirmish/lifecycle/AttackMove fixtures. Default play does not emit these rows.

The host captures the actual pre/post model state and receipt at `SubmitForOwner`, including stale-epoch rejection, then records relevant pre/post `Model.Advance(0.1f)` states and the post-advance simulated clock. The GameMode stamps raw snapshots with its trusted epoch before digesting. Host `Publish` and each local controller's received snapshot log the full visible player, unit, and resource records, including all four Guard fields. The controller logs only after its assigned owner ID is known. No private order accessor, gameplay mutation, or new human input binding is used.

Dot-source `unreal/Scripts/AreaGuardObservation.ps1` and call `Get-AreaGuardObservation -Logs @{host=<text>;rendered=<text>;observer=<text>} -RunId <token> -SourceTree <hash>`. The policy checks token/role/row/shape bounds, duplicate JSON keys, authoritative accepted owner-one Guard/post, actual host acquisition/chase/return/home advances, strict post leash, one movement budget, and matching full visible records plus ordinary digest lines at three-role common revisions. Client publication may skip intermediate revisions. The synthetic policy checks are in `test-area-guard-observation-policy.ps1`; their pass is **parser evidence only**.

Derive positions from the observed spawn/post, not hardcoded requested positions. If a separate override case is added, verify Guard clearing and absence of resumed autonomous motion. Keep the fixture opt-in and bounded; review its source and pure policy before launching it.
