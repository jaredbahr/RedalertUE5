# Group-order batch validation

The local order queue previously validated Move coordinates and Attack IDs at enqueue but deferred their snapshot eligibility until dispatch. A direct queue call could replace a valid pending order with an ineligible unit/target, report success, and later discard the replacement. Stop, Gather, ReturnCargo and AttackMove already checked snapshot eligibility at enqueue.

Every normalized intent now passes the existing `IsValidIntent` check before the staged queue is changed. Finite destinations are still clamped first. An invalid member rejects the whole proposed batch, preserving valid pending orders, their FIFO positions and the dispatch clock in the same snapshot/owner/epoch. Normal context synchronization and pruning still happen before staging: rejection does not retain stale orders after ownership, death or epoch changes. Authoritative server checks remain unchanged.

The native `QueueInvalidBatchIsAtomic` case seeds pending commands, dispatches two, then attempts a valid replacement followed by an invalid Move or Attack. It checks rejection, the original pending destination/identity, unchanged snapshot digest and pacing. Cases cover missing, foreign, dead and immobile movers plus missing, dead, friendly, same-team and unresolved-owner targets. Existing stale-snapshot coverage now starts with eligible commands and invalidates them afterward; its original empty-dispatch assertion remains. Clamp, legacy distinct-owner targeting, capacity, coalescing, FIFO, epoch and terminal coverage remain.

On Windows, `tests\run-group-order-queue-tests.cmd` and its `optimized` argument compile the actual production queue, selection, ReturnCargo, command-model and skirmish-rule sources with the existing portable UE subset. The runner requires all five exact queue groups and retains checks under `NDEBUG`. Its test-only ASCII digest bridge uses the Windows default MD5 provider and checks three known vectors; unavailable MD5 fails rather than changing provider policy. Portable checks do not establish an Unreal build, viewport input, rendered behavior or ordinary UI reachability of the invalid direct-call path.

## Actual validation and remaining limits

At source commit `b1e0a6808f8bd6e5d36ad4233c86d8a77a158ad2`, MSVC C++17 `/W4 /WX` compiled the actual production sources and the five native queue test bodies through the portable subset. The original queue, with the same corrected fixtures, produced 159 checks and 29 expected regression failures; the other four groups passed. The fixed queue produced **161 checks and zero failures across all five groups**, including the same-unit invalid replacement case and three digest vectors. Two extra assertions execute when the original pending command survives. Both used direct installed-compiler invocations with process-local include/library paths and no engine or host probes.

These are scoped functional observations, not a passed enclosing validation stage. The unchanged bounded owner reported an owned descendant after each root exited, requested owned cleanup, and confirmed zero survivors afterward. The normal candidate had native exit 0 but the outer stage still failed. A thin caller-console release adapter did not clear that failure; its cause remains unidentified. The first compiler attempt's `TEXT` macro collision and descendant failure are retained; the include-order correction removed the compiler error. Optimized and Unreal/native/runtime checks were not run. Do not infer that source checks, forced cleanup or zero survivors afterward pass the original clean-completion requirement.

This branch changes no Pawn, HUD, authoritative model, RPC, sampler, asset or existing acceptance artifact. Keep the change draft until its required integration and runtime evidence is reviewed; no merge or engine acceptance follows from this portable result.
