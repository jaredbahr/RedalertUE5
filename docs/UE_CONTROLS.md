# Manual UE command proof

This is a small engine-native correctness fixture, not a playable RA2 roster or a scale benchmark. Use the runtime proof launcher and generated gameplay map described in the [UE test plan](UE_TEST_PLAN.md). The existing `VisualProof` map in [UE setup](UE_SETUP.md) is the separate three-asset art review scene. No art approval is recorded.

## Controls

- Left-click within 40 screen pixels of an owned live unit's ground marker to select it. Clicking elsewhere clears selection.
- Right-click ground to request movement, or an enemy marker to request attack. The ground plane is world Z=0; no navigation or terrain raycast is implied.
- Press **P** to request one generic unit using the fixture's toy credits and production rule. Production does not require a building in this proof.
- Use the mouse wheel to change the fixed oblique orthographic camera width. The camera stays centered on the fixture origin; panning is not implemented.

Click the game viewport first if the editor has keyboard focus. Green markers identify owned units, red markers identify other owners, and yellow brackets identify the selected owned unit. The HUD shows the host-assigned owner, replicated snapshot revision, toy credits, selection, the last request sent, and a separate host **ACCEPTED/REJECTED** receipt with its sequence and reason. A receipt does not predict a state change: the views and credits still update only from snapshots.

Each client renders local, non-colliding static-mesh components from replicated unit records. Position, health, credit balance, production, ownership and death come only from the host snapshot; the presentation code does not predict or simulate them. Dead records remain in the host model but their views and selection disappear. The player controller supplies increasing request sequence numbers shared by its command paths; respawn/reconnection sequencing is outside this fixture. Manual orders are disabled when `-ProofAutomation` is active so they cannot disturb the scripted acceptance sequence.

If the local original generated Rhino mesh exists at `/Game/BlockoutGenerated/Meshes/SM_RhinoTank_Blockout`, every generic record uses that same mesh at **0.3 display scale** for the tiny command fixture. Otherwise it uses the engine basic cube. The records have no unit-kind field, so these views do not demonstrate infantry/vehicle differentiation, approved army scale, rigging, or finished art. The three-asset visual proof remains the place to review the original Tesla Reactor/Rhino/Conscript together.

## Manual acceptance checklist

Run a host plus two actual UE clients with graphics after the core and network smoke checks pass. This checklist requires visual/input inspection; NullRHI or successful compilation alone cannot pass it.

1. Both clients show their distinct assigned owner IDs, the same host revision/units, readable markers, and ground under the camera. The view works with generated assets and with the documented cube fallback.
2. Each client selects only its own living unit. Right-click ground: its requested movement appears in subsequent snapshots and both clients show the same final location. No local teleport should precede a snapshot update.
3. Right-click an enemy marker: host-owned combat changes health consistently on both clients. A dead unit's view disappears and cannot stay selected.
4. Press P: only the host changes credits and creates the unit, and both clients display the result. When credits are insufficient, the host rejects production without a local spawn or credit change.
5. Mouse wheel changes only the local view. Losing selection or clicking empty space produces no gameplay changes. Record any focus, projection, readability or HUD overlap problems as observed bugs.

Status: compilation, four native command test groups and the host/two-client NullRHI replication fixture passed; see [recorded evidence](UE_NATIVE_PROOF.md). No graphical pass or screenshot is claimed by this document. Internet traversal, packet loss/latency handling, eight players, large armies, pathfinding and a complete bot skirmish remain separate gates.

## Bounded engine-rendered controls scenario

After building the native module and generating the CommandProof map, run:

```powershell
& .\unreal\Scripts\test-controls-proof.ps1
```

The runner first performs a separately bounded standalone graphical warmup (`-game`, `-RenderOffscreen`, 1280x720, `-ProofGraphicsWarmup`), using a reusable cache at `generated/controls-cache` on D:. After the normal snapshot-derived proxy views are created/updated, the local camera pawn polls `FAssetCompilingManager::Get().GetNumRemainingAssets()` and waits for a valid 1280x720 viewport plus zero remaining assets continuously for at least two real monotonic seconds and three game ticks before requesting exit 0. It logs pending state at most once per second and a completion marker with remaining count, idle seconds, frame count and viewport dimensions. The runner additionally requires that marker, RHI/map initialization and successful exit within **300 seconds by default**; `-WarmupTimeoutSeconds` accepts a finite limit up to 600. This warms initialization, not screenshot or controls acceptance. The manager API is declared by Engine's `AssetCompilingManager.h`; the installed shader compiler registers with that manager, so no direct RenderCore dependency is added. Zero registered asset jobs does not prove all possible RHI/GPU work is drained.

Only after warmup succeeds does the runner start the strict scenario clock and launch one dedicated NullRHI host, one actual rendered UE client at 1280x720 (`-RenderOffscreen`), and one passive NullRHI observer. It waits for the rendered client to acquire owner 1 and a valid viewport before admitting owner 2. The scenario remains bounded to 90 seconds; the default combined process runtime budget is **300 + 90 = 390 seconds**, with a maximum of 600 + 90 = 690 seconds, plus polling/cleanup overhead. Cache/temp overrides remain process-local, scenario processes receive two reported cores each, and cleanup is restricted to processes this run started. It changes no firewall, global environment, security setting or installation. Existing cache entries are reused without deleting prior evidence or other project files.

Every owned UE role receives the process-only `DevOptions.Shaders/WorkerProcessPriority=0` (Normal) override. Warmup additionally receives `-CoreLimit=4` and thread keys `NumUnusedShaderCompilingThreads=1` and `NumUnusedShaderCompilingThreadsDuringGame=1`. These are per-invocation overrides, not persisted project/engine settings. Installed `ShaderCompiler.cpp` reads the thread keys from `GEngineIni` around lines 1150–1153 and selects reported cores minus one when the core count is at most four around lines 1182–1193; three workers are therefore expected for warmup, but the actual reported count is recorded from its log. Installed `BaseEngine.ini` around lines 2142–2143 documents worker priority 0 as Normal, with default -1. `Core/Private/Misc/ConfigCacheIni.cpp` documents and parses the `-ini:Engine:[Section]:Key=Value,[Section]:Key=Value` syntax around lines 1633 and 2239. Worker priority, thread settings and optional shader overrides share one Engine.ini argument. The reported two-core controls scenario and its assertions remain unchanged.

Reported `CoreLimit` values size thread pools; they are not an OS CPU allocation. Separately, the runner chooses the first two logical CPUs in its invoking process's allowed affinity mask and immediately applies that same affinity to every UE process it starts, at Normal process priority. It then polls once per second and repairs observed affinity/priority changes. UE processes must still match this run's exact PID, start time and executable path. Shader workers are claimed only when process metadata identifies a currently verified owned UE parent, their creation time agrees with their actual start time (within metadata precision), their executable is the installed ShaderCompileWorker, and their command line belongs to this project. Their exact identity is retained for later policy checks and cleanup. An unavailable ownership-metadata query aborts the run with an explicit error; unrelated workers are never claimed by name alone.

JSON records process identities, policy checks, observed resets and reapplications (up to 256 events, with truncation flagged), and discovery failures. Even the warmup's three workers are intended to share the same two CPUs. This is a **polling policy**, not a hard OS sandbox or proof of continuous confinement: assignment follows `Start-Process`, workers can spawn between checks, and UE has actually reset the initially verified mask from 3 to 255 during startup. A separate root monitor manually reapplied mask 3 during the clean-start `2643bf8` attempt; that evidence must not be described as confined throughout or as verification of this newer runner. The runner changes no other projects, system scheduling configuration or unrelated processes.

The cheap `unreal/Scripts/test-controls-policy.ps1` test exercises the actual runner helper functions with mocked process metadata only. It checks owned parent/worker policy, untouched foreign workers, recorded repair after an affinity reset, untouched reused PIDs and fail-closed metadata errors. It launches no engine and mutates no real process; it is not graphical acceptance or proof that Windows preserves worker affinity.

`-ProofControlsAutomation` is separate from the original `-ProofAutomation` RPC smoke. The rendered pawn projects snapshot positions into its actual viewport and supplies those screen coordinates to the **same** selection and right-click handlers used by manual controls. Both paths share the pointer resolver and ground `DeprojectScreenPositionToWorld` calculation. Assertions cover enemy selection refusal, owned selection, empty-space clearing, zoom in/out, projection/deprojection round trip within 2 cm, accepted movement and destination arrival, accepted attack and replicated target damage, and production with the exact host-owned unit/credit delta. All orders use controller RPCs and host receipts; no test-only state mutation or direct model submission occurs. A fourth accepted move separates the original unit from its new spawn for the final screenshot.

Viewport readiness admits the observer but does not start the rendered client's scenario clock. The separate `PROOF_CONTROLS_SCENARIO_READY` marker requires explicit owner records 1, 2 and 100; the selection scenario and its 23-second client exit are anchored to that first shared snapshot. This prevents a slower observer startup from shortening the rendered client's participation.

Optional `-UnoptimizedShaders` is a functional-rendering debug mode, disabled by default. A single process-only Engine.ini override string applies `r.Shaders.Optimize=0` under both `[ShaderCompiler]` and startup `[ConsoleVariables]` consistently to warmup and scenario processes. It still compiles shader programs and keeps all controls, snapshot and screenshot gates. Installed `ShaderCompiler.cpp` around lines 3513–3517 adds `CFLAG_Debug` when optimization is disabled unless a shader forces optimization; `D3DShaderCompiler.cpp` around lines 1362–1374 maps that to FXC's `D3DCOMPILE_SKIP_OPTIMIZATION` instead of level 3. `ConfigCacheIni.cpp` around lines 6664–6665 applies startup Engine `[ConsoleVariables]`; that matters because `ShaderCore.cpp` gives an enabled global CVar precedence. The rendered viewport logs the actual IConsoleManager value as `PROOF_CONTROLS_RENDER_CONFIG shadersOptimize=N`, and the runner requires it to match the requested mode. JSON records the requested and observed configuration. This may reduce compilation cost but does not reduce required permutations or prove faster startup. Unoptimized shaders can change GPU cost and floating-point results, so such a run is not a performance or production-rendering claim.

The runner also polls a **soft** storage guard at startup and every ten seconds: reusable D: controls-cache defaults to 2048 MiB and this run's D: temp directory defaults to 1024 MiB. `-MaxCacheMiB` and `-MaxTempMiB` can lower/change those limits; zero disables the corresponding threshold. Exceeding a threshold aborts the run through owned-process cleanup and preserves files for review. JSON records last/peak observed bytes and check counts. This is not a filesystem quota: growth can overshoot between polls, and project Saved/Intermediate, driver caches and OS writes are outside these two monitored directories. It deletes nothing and relocates no global cache. C: cache observations are recorded separately; configured D: paths do not prove zero C: writes.

The host independently commands two bot units through normal authoritative submission: a mover must reach its destination, and an attacker damages owner 2's passive unit. Rendered owner 1 attacks a separate stationary owner 100 target, so its attack cannot substitute for bot damage. The fixture begins with two human-owned units and three bot-owned units. One production request adds a sixth record; dead records remain in snapshots. Final counts describe the 20-second scenario observation boundary, before client/process shutdown. These tiny observed counts do not establish an army-size budget.

Fresh output goes under `generated/controls-<UTC timestamp>/`: warmup/host/rendered/observer logs, `result.json`, and two requested UE screenshots (`01-selected.png`, `02-moved-combat-produced.png`). The runner requires successful scenario markers/assertions, all four accepted receipts, at least three equal snapshot digests shared by all scenario processes, observed initial/final owner/unit counts, and fresh 1280x720 PNGs with valid signatures and nontrivial byte sizes. JSON records tested HEAD, dirty-source flag, UTC start/end, separate warmup/scenario/total stopwatch durations and timeout budgets, stages, reusable cache path, observed counts, common revisions, screenshot hashes and any failure. File checks establish capture provenance; a person must inspect the images for HUD/marker readability and scene contents.

This is **engine-rendered functional automation**, not physical mouse, keyboard, window focus or touch validation. It supplies viewport coordinates through a scenario cursor rather than moving the operating-system pointer. Native UI automation is unavailable in this environment. Manual viewport focus and actual device inputs remain unchecked. Host rejection text is surfaced by the HUD, but this finite scenario tests accepted commands; resource rejection remains in the manual checklist and core tests. No run is claimed until its logs, JSON and rendered images have been reviewed.

Command evidence records and requires the actual sequence/type pairs **1 Move, 2 Attack, 3 Produce, 4 Move** alongside host receipts. Both ground-order stages first require `FindUnitUnderCursor(false) == INDEX_NONE` in the actual viewport. The first destination is now `(-300,-300,0)` rather than a point near the enemy's screen-space pick radius; attack separately requires picking the intended snapshot target. Successful assertions log once per evidence key while waiting for replicated movement/damage.

Owned launches enable diagnostic-only `LogDerivedDataCache Verbose`. JSON counts actual Pak cache-hit messages by Engine `DerivedDataCache/Compressed.ddp` or `DDC.ddp` path. Global hits require a `GlobalShaderMap/` key. `materialRelatedHitCount` is a request/key-path heuristic that can include EngineMaterials textures; it does not claim material-shader hits. Separate examples retain the actual keys and requests. This uses the successful-hit log in installed `PakFileCacheStore.cpp` around lines 764 and 850; merely opening a Pak is not counted. Diagnostics are collected even for failed runs and do not relax or add an unverified cache-hit acceptance gate.
